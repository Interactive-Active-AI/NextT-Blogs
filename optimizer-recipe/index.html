Eight Learning Rates and Three Schedules: Reading NextTransformer's optimizer recipe

NextTransformerNovember 2026About 9 min read

The optimizer is usually the part of a training run people tune. Here it is the part nobody is allowed to touch, and that constraint shapes every number in it.

01A frozen optimizer is part of the instrument

NextTransformer compares architectures. Everything that is not the architecture has to be held still, or a comparison measures the tuning budget instead of the design. So the optimizer is pinned by the protocol, down to the beta values of individual scalar groups, and the pinned values are hashed into the fingerprint that every published result carries.

That inverts the usual incentive. A tuned recipe wants to be the best recipe for the model in front of it. A frozen recipe wants to be the least surprising recipe across models it has never seen, because the next architecture someone submits will have to live with it. Reading the code with that in mind makes several choices legible that otherwise look arbitrary.

Everything below is in nexttransformer/native/optimizer.py and nexttransformer/protocol/spec.py. The protocol's base rates are five numbers:

02Two scalars carry the transfer

Between the base rates and the rates in the optimizer sit two multipliers, and they answer two separate questions.

Both are written as ratios against a reference point rather than as absolute formulas, and the reference point is the model the rates were originally tuned on: nanochat's d12, width 768, with a 219-token batch. The recipe is not claiming to know the right learning rate for an arbitrary model. It is claiming to know how to move a rate it trusts to a model of a different width and a different batch.

The protocol runs at 220 tokens per update, so bscale is exactly √2 for every registered run, and it is the square-root batch rule: double the batch, raise the rate by √2. The width rule is the inverse square root, so a width-1,280 model gets 0.775 of the reference rate and a width-2,048 model gets 0.612.

03Not one learning rate, eight

The recipe does not have an optimizer with a learning rate. It has eight or nine parameter groups, each with its own rate, its own betas and its own weight decay. Table 3 is the whole thing.

Three details in that table are easy to read past.

The betas are not shared. Embeddings run β₂ = 0.995 while the output head runs 0.96, a difference of roughly an order of magnitude in the effective averaging window of the second moment. Embedding gradients are sparse — a given token's row is touched only when that token appears — so a long window is how you get a usable second-moment estimate at all. The output head sees every example and does not need one. The x0 lambdas invert the usual arrangement entirely, with β₁ = 0.96 above β₂ = 0.95.

eps is 1e-10 across every AdamW group, four orders of magnitude below the common 1e-8. With a tiny eps, Adam stays close to pure sign-like normalization even where gradients are small, instead of quietly becoming SGD in the small-gradient regime.

The smear gate is the one rate that never scales. It is a fixed 0.2, untouched by batch or width. Every other group in the model moves when the batch moves; this one is pinned, which reads as a gate whose useful rate is a property of the gate rather than of the run.

3.1Where width scaling lands, and where it does not

Only three groups get dscale: the output head, the token embedding and the value embeddings. Muon does not. The scalars do not. The auxiliary AdamW groups do not.

That line falls exactly where the parameters are indexed by vocabulary rather than by width — the matrices whose fan-in grows with the model while the number of gradient contributions per row does not. The block matrices are left to Muon, whose update is orthogonalized by a Newton–Schulz iteration and therefore already has a norm set by the iteration rather than by the gradient scale. Reading it that way, the recipe applies width transfer precisely where the update rule does not supply it.

3.2Covering every parameter exactly once

After the groups are built, the code collects every unclaimed parameter, sorts two-dimensional ones into Muon buckets keyed on tuple(p.shape) and everything else into a scalar AdamW group, and then asserts that the groups cover the model's parameters exactly once — no duplicates, no omissions.

For a repository that accepts architecture submissions from outside, this assertion is doing real work. The failure it prevents is not a crash; it is a new module's parameters silently receiving a default rate, or two, and a result being published on a run nobody knew was misconfigured. The bucketing by shape is a separate concern: Newton–Schulz is a batched matrix operation, so same-shaped matrices have to travel together.

04Weight decay is a parameter count in disguise

The protocol lists weight decay as 0.28. No parameter is decayed by 0.28.

Those two constants are the matrix parameter counts of nanochat's d12 and d24. The rule is nanochat's: decay scales inversely with the number of matrix parameters, so a bigger model is decayed less per parameter. The 0.28 is a rate expressed in d12 units, and the ratio converts it to the model actually being trained.

It is a small piece of engineering with an outsized role, because a hyperparameter rule that silently changes meaning across a size sweep would contaminate the size curve the sweep exists to measure.

05Three schedules running at once

There is one function that sets schedules, and it moves three different things on three different curves.

Learning rate. Forty updates of linear warmup, then flat, then the final 65% of training decays linearly to 5% of peak. A 65% warmdown is long by convention; most of the run is spent on the way down rather than at the top.

Muon momentum. It climbs from 0.85 to 0.97 over the first 400 updates, holds at 0.97, and then falls to 0.90 across the warmdown — on the same boundary where the learning rate starts dropping. Early on, when the weights are moving fastest, the momentum buffer holds the least stale history. Late on, as the rate decays, momentum is released rather than tightened, which keeps the effective step from collapsing as fast as the rate alone would make it.

Muon weight decay. A cosine from its full value at step 0 to zero at the end, independent of the learning rate curve. Regularization is strongest while the model is still choosing what to represent and is gone by the time it is settling.

The learning-rate schedule is the one everyone writes down. The other two are the ones that would be silently different between two submissions if the protocol did not pin them.

06What is deliberately absent

There is no global gradient clipping. For a frozen protocol that is a deliberate position: a global clip is a safety net that also quietly rescales the comparison whenever one architecture's gradients are larger than another's, and it would make instability look like a tuning difference rather than a property of the design.

What exists instead is two targeted clips, applied after gradient accumulation and before the step, to exactly the components that need them — Circle's halter and the loopformer's conditioner. Both are architecture-specific control paths rather than ordinary weights. The pattern generalizes to new submissions: an exception is allowed, it is named, and it is preregistered before pilots rather than discovered during them.

07What we do not know

Honesty about the limits matters more here than usual, because the recipe is frozen and will not be re-tuned per submission.

The base rates were tuned on one model at one width with one batch size. The two transfer scalars are standard rules, not measurements on this codebase, and nothing in the repository currently demonstrates that the square-root batch rule and the inverse-square-root width rule hold across the full range the scaling study will cover. The T3 study spans widths 1,024 to 2,048, which is where that assumption first gets tested at four points on one compute budget — and if it fails, it will show up as curvature in the size curve that has nothing to do with architecture.

The per-group betas and decays are inherited, and we have no ablation isolating any one of them. The routing coefficients for the mixture-of-experts families are explicitly marked as pilot settings rather than a registered recipe.

None of this undermines the comparison the protocol is built to make. Every architecture meets the same recipe, so a difference between two results is still a difference between two designs. It does mean the recipe is a fixed choice rather than a demonstrated optimum, and the size curve is the first thing that will tell us how good a choice it was.
